# DBPanda 产品路线图

本文是**功能规划的唯一事实来源**。新需求先进本文评分排期，再动代码；每完成一项回来改状态。
实现约定见 [开发规范](开发规范.md)，AI 相关见 [大模型](大模型.md)。

> 基线：v2.6.2（2026-08）。当前功能面已接近 Navicat 完整版，继续补同质功能边际收益很低。

---

## 一、产品定位判断

Navicat 是通用型国际产品，对**国内合规、国产数据库、分库分表、DBA 运维深度**几乎不投入。
DBPanda 的取胜路径不是"功能更全"，而是在这几条线上做到 Navicat 结构性做不到的深度。

两条不可动摇的产品原则：

1. **全本地、无后端。** 凭据、审计、快照一律留在本机（主进程加密）。这是安全叙事的地基，
   也是相对 Navicat Cloud 的差异，任何功能不得以"要建个服务端"为前提。
2. **危险操作必须有网。** 预检 → 审批 → 审计 → 可回滚，形成闭环。

> 曾有第三条"数据出口统一收口"，它是敏感数据脱敏的配套原则；脱敏于 2026-08-18 搁置后一并撤下。

## v2.7.0 —「三大旗舰」（重点版本）

> 卖点：一条 SQL 打穿 32 个分库，也能跨库 join；改错了还能撤回。

这一版把三个差异化最强的功能一次做完，形成完整叙事：**批量、跨库、可回退**。
体量明显大于常规版本，因此**先建共用地基，再按 M1–M4 里程碑推进**。

### 0. 共用地基（必须先于三项功能落地）

三个功能不是三条独立的线，它们共享两块基础设施。地基做对，三项各省一半工作量；地基做歪，三项一起返工。

| 地基 | 服务于 | 说明 |
|---|---|---|
| **多连接并发执行器** `src/main/multiExec.js` | 广播 / 联邦 | 并发上限、逐库超时隔离、统一取消、错误归集。广播是"并发执行同一条 SQL"，联邦是"并发从多源取数"，调度逻辑同源 |
| **本地加密快照存储** `src/main/localStore.js` | 后悔药 / 联邦 | 后悔药存受影响行原值，联邦存拉到本地的临时表，共用同一套加密、配额与按天数/份数自动清理 |

> 硬约束：本地落盘的行数据一律走 `localStore.js` 的加密存储，不得明文落在 userData 下；
> 存进去的必须是**明文原值**——见下方「两条通用数据流结论」的第 2 条。

### 里程碑与实施顺序

| 里程碑 | 内容 | 依赖 | 量级 |
|---|---|---|---|
| **M1** | 共用地基两件：`multiExec.js`、`localStore.js` | 无 | 低 |
| **M2** | 多库广播执行 | M1 并发执行器 | 低 |
| **M3** | SQL 后悔药 | M1 加密快照存储 | 中 |
| **M4** | 跨库联邦查询 | M1、M2 的并发取数 | 高 |

M2 排在 M4 前，是让并发取数逻辑先在简单场景（同构广播）验证稳当，再拿去跑复杂场景（异构联邦）。
M3 与 M2 无依赖关系，排在中间是因为它风险高于广播、低于联邦，先落地能更早暴露 `localStore.js` 的设计问题。

### 发布策略与风险

- **风险**：M4 联邦查询是三项里唯一的高成本项，有拖住整版发布的可能。
- **底线方案**：M4 设"受限版"下限——只支持 `SELECT`、每源表单次拉取上限 10 万行、
  仅本地内存计算并明确标注"非一致性快照"。达到这条下限即视为可发布，性能优化与更多语法放到后续小版本。
- M1–M3 任一未达验收，整版推迟，不单独发半成品（见第四节"明确不做的事"）。

### 1. 多库广播执行（M2）

- **痛点**：分库分表 / 多环境下，同一条 SQL 要在 N 个库重复执行，现在只能开 N 个标签页。
- **范围**：
  - 选择一组连接/库，支持通配（`order_db_*`）与手动多选，保存为"广播组"。
  - SELECT 结果纵向合并，自动追加"来源连接 / 来源库"列；DDL/DML 输出成败矩阵，失败项可单独重试。
  - 并发上限可配置，逐库超时隔离，单库失败不影响整体；支持整体取消（复用适配器已有的逐请求取消）。
  - 生产库成员仍走既有审批（[safety.js](../src/main/safety.js)）：一次广播对同一操作确认一次，不逐库重复弹窗。
  - 附带「多环境对比」：同一条 SQL 在 dev/test/prod 跑完并排 diff。
- **不做**：不做分片路由解析，不解析 ShardingSphere 规则；不做跨库聚合（那是联邦查询的事）。
- **验收**：32 个 SQLite 库广播 `SELECT`，结果带来源列正确合并；其中一个库故意报错，其余成功且错误可见可重试；
  执行中点取消，全部会话 2 秒内释放。
- **涉及**：`multiExec.js`、[base.js](../src/main/db/base.js)、[ipc.js](../src/main/ipc.js)，新增 renderer `broadcastTab.js`。

### 2. SQL 后悔药 / 回滚中心（M3）

- **痛点**：`UPDATE` 漏写 WHERE 是最高频事故，事后只能求 DBA 恢复备份。三项里情绪价值最强、最易自发传播。
- **范围**：
  - DML 执行前，复用 [impact.js](../src/main/impact.js) 的影响行集，把**受影响行原值**快照到 `localStore.js`（加密）。
  - 回滚中心保留最近 N 次操作，可预览反向 SQL（UPDATE 反写 / DELETE→INSERT / INSERT→DELETE），
    可整体或按行选择性回滚；回滚本身也进审计。
  - 超过行数阈值（默认 5 万）或表无稳定唯一主键时不做快照，明确提示改走备份，**不静默降级**。
  - 快照按份数与天数自动清理，占用可见可手动清空。
- **不做**：不承诺 DDL 回滚；不承诺并发写入下的一致性——回滚前必须展示
  "快照时间 + 当前值已被他人改动"的冲突提示，冲突行默认跳过。
- **验收**：对 1 万行表执行漏写 WHERE 的 UPDATE，回滚后逐行比对与快照前完全一致；
  某行在期间被他人改动时，回滚前给出冲突警告并可跳过；无主键表明确拒绝并给出理由。
- **涉及**：新增 `src/main/undo.js`，复用 [sqlGenerator.js](../src/main/sqlGenerator.js) 与 `localStore.js`。

### 3. 跨库联邦查询（M4）

- **痛点**：微服务拆库后，"订单库的订单 join 用户库的用户"所有客户端都做不了，用户只能导出两份 CSV 用 Excel 拼。
  三项里最稀缺、最能引发口碑传播的一项。
- **范围**：
  - 内置本地引擎（DuckDB 优先，退路是复用已有的 sql.js / better-sqlite3），
    支持 `SELECT ... FROM [连接A.库.表] JOIN [连接B.库.表]`。
  - 同时支持"把上一个结果集当表继续查"，与结果集图表打通。
  - 各源表并发拉取走 `multiExec.js`，类型映射复用 [transfer.js](../src/main/transfer.js) 的跨方言映射表，
    本地临时表落在 `localStore.js` 并在标签关闭时清理。
- **受限版下限（发布底线）**：只支持 `SELECT`；每源表单次拉取上限默认 10 万行，超限**明确拒绝**
  而非静默截断；界面常驻标注"本地内存计算、非跨库一致性快照"。
- **不做**：不做谓词下推优化（后续小版本再做）；不支持跨库写入；不承诺事务语义。
- **验收**：MySQL 表与 PostgreSQL 表 join 的结果与手工导出比对完全一致；超限时明确拒绝并提示改用数据传输；
  临时表在标签关闭后确实清理（磁盘占用归零）。

  已提取到下一节保留。

### 两条通用数据流结论

下面两条是做脱敏设计时读代码发现的**既有事实**，与脱敏是否实现无关，做其它功能时应当继续引用。
原设计稿已删除，结论保留在此。

**1. 渲染层所见的行数据，直接决定 UPDATE/DELETE 的 WHERE 条件**

[grid.js](../src/renderer/js/grid.js) 的 `getPendingEdits()` 用渲染层自己持有的行数据拼出主键对象，
经 `db:applyEdits` 传到 [base.js](../src/main/db/base.js) 的 `buildEditSql()`，
由 `whereOf()` 直接拼进 `WHERE`。

因此**任何会改变渲染层所见行数据的功能，都会连带改写写操作的定位条件**——
显示层的改动会变成数据正确性事故：轻则影响 0 行（用户以为改了其实没改），
重则匹配到别的行（改错数据）。虚拟列、单位换算显示、值格式化、脱敏一类的功能都会踩这个坑。

通用解法是**行令牌**：主进程为每行下发一枚不可逆 token，真实主键留在主进程内存，
渲染层编辑时回传 token 再还原。架构上已有现成通道——`tableData` 本就在下发
`rowIdColumn` / `rowIds`（PG 用 ctid 之类的系统行标识让无主键表可编辑），`_pkOf()` 已优先使用它。

**2. 「数据搬运」与「数据出境」必须区别对待**

| 类别 | 例子 | 规则 |
|---|---|---|
| **数据搬运**：库→库，或进入本工具的加密存储 | 数据传输、结构/数据同步、备份、后悔药快照、联邦临时表 | **一律存明文原值**，只做加密落盘 |
| **数据出境**：进入人眼、剪贴板、用户可读文件、第三方网络 | 网格、单元格查看器、复制、导出文件、AI 发送 | 需要过滤时在这一层做 |

搬运物一旦被改写（脱敏、截断、格式化），后果是**功能错误而非显示问题**：
回滚会把改写后的值写回数据库、联邦 join 结果全错、备份不可还原。
v2.7.0 的 `localStore.js` 硬约束就是这条的直接落地。

## v2.8.0 —「安全网与规范」

> 卖点：结构改过什么都有版本，上线前先过审。

1. **Schema 版本时光机（P1）**：结构变更自动快照 → 时间线；任意两版对比生成迁移与回滚脚本；
   可导出 Flyway / Liquibase 格式；可写入用户自己的 Git 仓库（本地路径，不联网托管）。
   复用 [sync.js](../src/main/sync.js) 的结构对比引擎，成本低。
   **验收**：加列 → 改类型 → 删列三次变更后，能回放出任意中间版本的 DDL 与回滚脚本。
2. **SQL 规范审核与评分（P1）**：DDL/DML 执行前检查——无主键、大字段滥用、缺索引、`SELECT *`、
   无 WHERE 的 DML、命名规范、字符集不一致等，输出评分与逐条修改建议，规则可开关。
   生产连接可设"低于 X 分禁止执行"，与既有审批串联。
   **验收**：违反 5 条规则的建表语句，评分与命中项完全正确，修复后满分。
3. **列画像（P1）**：表数据页侧栏显示每列空值率、去重数、Top 5 取值分布、数值列直方图；按需触发不拖慢首屏。
   **验收**：百万行表点"画像"，采样统计 3 秒内返回并明确标注"基于采样"。

## v2.9.0 —「DBA 深度」

> 卖点：一键出巡检报告，慢 SQL、缺失索引、复制延迟一屏看完。

1. **数据库体检报告（P1）**：慢 SQL Top N（`performance_schema` / `pg_stat_statements` / 慢日志）、
   缺失与冗余索引、无主键表、碎片率、连接数、主从延迟；生成可导出的 HTML/Excel 报告，
   复用 [dataDict.js](../src/main/dataDict.js) 的导出管线，可挂到 [scheduler.js](../src/main/scheduler.js) 定时出报告。
2. **实时监控仪表盘（P2）**：QPS/TPS、连接数、锁等待、缓冲池命中率、复制延迟折线图，由现有"进程列表"升级而来。
3. **测试数据生成器（P2）**：按列类型 + 语义生成中文姓名/手机号/地址/日期，外键关联保持一致，
   支持批量万行，走已有导入的批量事务通道。

## v3.0.0 —「AI 闭环」

> 卖点：AI 从聊天框变成能干活的助手。

1. **AI 闭环四件套（P1）**——把 AI 接到已有能力上形成闭环，而不是再做一个对话框：
   1. **NL→SQL→图表一条龙**：本地建立表/列/注释索引供检索，生成 SQL → 执行 → 直出图表，每步可见可改。
   2. **批量补注释回写**：根据表名列名与样本数据生成中文注释，人工勾选后一键 `ALTER ... COMMENT`。
   3. **优化闭环**：执行计划 + 表统计 + 索引现状 → 输出可执行的索引 DDL 与预期收益。
   4. **报错即诊断**：错误面板直接给"原因 + 修复后 SQL"按钮。
   - **硬约束**：出站内容发送前必须展示实际提交了什么（沿用现有 AI 面板的告知机制），
     由用户自己判断是否包含不宜外发的数据。
2. **可视化查询构建器（P2）**：拖表、连线、勾字段生成 SQL，与编辑器双向同步。
   这是**相对 Navicat 的明确缺口**，评测对比会被扣分。
3. **记录全景视图（P2）**：选中一条记录，顺外键把关联子表聚合成"档案卡"，客服与运营排查场景。

## 四、明确不做的事

| 不做 | 原因 |
|---|---|
| 自建云同步服务 | 一旦有后端就要背运维、安全与数据出境责任，直接违反"全本地"原则 |
| 重的变更工单 / 审批流 | 那是 DBA 平台（Bytebase / Archery）的地盘，桌面端做不深，只会让界面臃肿 |
| 盲目堆数据库数量 | 每多一种都是长期适配债，只做有真实诉求的 |
| 报表设计器 | Navicat 有，但使用率极低，投入产出比差 |

## 第 1 批：MySQL 协议族（复用 `mysql2`，边际成本最低）

### ✅ 已完成（2026-08-19），4 种类型均已上线

| 类型 | 适配要点 |
|---|---|
| **TiDB** | 无存储过程/触发器/事件，但**有序列**（MySQL 没有的扩展）；`KILL TIDB` 才能跨节点终止会话；EXPLAIN 列与 MySQL 完全不同，不套用 MySQL 的优劣着色；序列会混进 `SHOW FULL TABLES`，已从表清单剔除 |
| **PolarDB for MySQL** | 对客户端与原生 MySQL 完全一致，**只做品牌与版本识别**，不覆盖任何元数据或 SQL 行为；连的若不是 PolarDB 会如实标注，不替用户改写版本串 |
| **StarRocks** | OLAP：网格只读、无显式事务、无存储过程/触发器/序列、EXPLAIN 为文本计划；**禁用可视化表设计器**（建表需 `DISTRIBUTED BY` 与表属性）；用户管理暂不开放（无 mysql.user，权限视图各版本差异大，待真实集群验证） |
| **Apache Doris** | 与 StarRocks 同源，直接继承其适配器，仅覆盖版本识别（无 `current_version()`，产品标识在 `version_comment`） |

新增的 `designerReason` 机制（[base.js](../src/main/db/base.js) + `design:meta` + `designer` 能力位）
让"建表语法差异过大"的方言可以明确关掉设计器，而不是生成一段必然失败的 DDL。

**⚠ CI 覆盖缺口（未解决，需要后续处理）**：这三个引擎**进不了现有的 service container 矩阵**——
GitHub Actions 的 service container 不能覆盖镜像启动命令，而 TiDB 单机要 `--store=unistore`、
StarRocks / Doris 的 all-in-one 镜像要跑自带启动脚本并暴露多个端口。
目前已在 [integration-db.js](../scripts/integration-db.js) 登记了 `TIDB_` / `POLARDB_` /
`STARROCKS_` / `DORIS_` 前缀，可指向自建实例手动验证。
要进 CI 需改成 `docker run` 步骤而不是 services，属于独立的一件事，**在真机验证前这四种类型应视为未经端到端验证**。

## 第 2 批：PostgreSQL 协议族（复用 `pg`，一个协议吃掉一片信创目录）

### ✅ 已完成（2026-08-19），3 种类型上线

| 类型 | 适配要点 |
|---|---|
| **人大金仓 KingbaseES** | 默认端口 **54321**、超级用户 `system`、默认库 `test`，与原生 PG 都不同；国密 sm3 认证时把驱动报错翻译成服务端改法 |
| **openGauss / GaussDB** | 见下方认证专项；版本识别要处理 `GaussDB Kernel 505.1.0` 这种把产品名和版本号分开写的格式 |
| **Greenplum** | 版本号在 `version()` 的括号里（`PostgreSQL 9.4.24 (Greenplum Database 6.25.3 …)`），父类为显示做的截断会丢掉它，需单独取出 |

为此在 [postgres.js](../src/main/db/postgres.js) 保留了 `serverVersionRaw`：
父类为界面显示会把 `version()` 截断成 `PostgreSQL x.y`，而三个分支的产品标识都在被截掉的部分里。

**openGauss 认证——路线图原先标注"开工前必须先验证"的那条，结论如下**：

openGauss 默认 `password_encryption_type = 2`，用的是自研 SHA256 认证，**不是**标准 SCRAM-SHA-256，
`node-postgres` 无法完成握手。核对驱动源码后确认它会以三种形态失败：
`Unknown authenticationOk message type`、`SASL: Only mechanism(s) … are supported`、
`SASL: SCRAM-SERVER-FIRST-MESSAGE: …`——三句话用户都看不出该改什么。

处理方式：**不引入 openGauss 官方的 node 连接器分支**（多一个 pg 驱动会长期分叉维护成本，
而服务端改一个参数即可兼容标准驱动），改为识别这三种签名并翻译成可操作指引
（改 `password_encryption_type`、改 `pg_hba.conf`、**重设一次密码**——改参数不会重算已有口令摘要，
这一步最容易漏）。非认证类错误原样抛出，绝不吞掉真实原因；两者都有自检用例覆盖。

**未纳入的分支**：瀚高 / Vastbase / IvorySQL 等在适配层面与原生 PostgreSQL 没有差异，
**直接用 PostgreSQL 类型即可连接**，不单独占一个类型——新建连接菜单已有 14 项，
再加三个几乎相同的条目只会让用户更难选。若信创投标明确要求菜单里出现这些名字，再按薄别名补。

v2.6.2 修的 PostgreSQL 9.6 兼容问题（`prokind` / `pg_sequences` / 标识列）在这批直接兑现：
openGauss 内核基于 PG 9.2、Greenplum 6 基于 PG 9.4、KingbaseES V8R6 约为 PG 10，
三者都会命中那些降级分支。

**⚠ 与第 1 批相同的验证缺口**：这三种类型同样没有公开可用的 GitHub service container
（KingbaseES 与 openGauss 的镜像需授权或需自定义启动），**未经真机端到端验证**。
[integration-db.js](../scripts/integration-db.js) 已登记 `KINGBASE_` / `OPENGAUSS_` / `GREENPLUM_` 前缀，
可指向自建实例验证。能在本地验证的只有版本识别与认证翻译逻辑，已进自检。

## 第 3 批：达梦 DM（信创硬门槛，成本与风险最高，单独立项）

## 第 4 批：原生 Oracle ✅ 已完成（2026-08-19）

**提前到达梦之前做**：Oracle 成本中等、企业市场绕不开，而且**有公开镜像可以真机验证**
（`gvenzl/oracle-free`，本机 Docker 与 CI 都跑得起来，不需要覆盖启动命令），
在一堆未验证类型上再叠一个验不了的达梦不是好节奏。

**实测确认：Thin 模式不需要任何原生模块。** 把 `oracledb` 的 `build/` 目录整个删掉后
`require` 仍成功、`thin === true`，且能真正发起 TCP 连接。因此：
不存在 Electron ABI 重建问题、用户无需安装 Instant Client、
打包排除掉 2.5MB 的 Thick 模式二进制后**净增约 1.5MB 纯 JS**。

**先做了纯重构**：抽出 [oracleBase.js](../src/main/db/oracleBase.js)（540 行方言）+
[oboracle.js](../src/main/db/oboracle.js)（120 行 mysql2 传输），
[oracle.js](../src/main/db/oracle.js) 提供 oracledb 传输。
切分用大括号匹配程序化完成，未手抄任何一行；重构后自检零变化才接新传输。
数据字典的兼容性修复从此一次生效于两边。

**途中发现的真问题**：`oracleBase` 原来的事务用 `SET AUTOCOMMIT = 0/1`——
那是 OceanBase 接受的 MySQL 写法，**真 Oracle 会报 ORA-00900**
（`SET AUTOCOMMIT` 是 SQL*Plus 的客户端命令，不是服务端 SQL）。
已改为两个子类各自实现：OB 继续用 SQL，原生 Oracle 用驱动的 `autoCommit` 选项，
通过两个哨兵字符串在基类的「以 SQL 驱动事务」模型里表达。

**为无损做的四件事**（oracledb 的默认行为全是坑）：

| 默认行为 | 后果 | 处理 |
|---|---|---|
| NUMBER → JS number | `NUMBER(38)` 静默丢精度 | 按字符串取回，同 MySQL 的 `bigNumberStrings` 思路 |
| CLOB/BLOB → Lob 流对象 | 界面与导出拿不到内容 | CLOB→字符串、BLOB→Buffer |
| DATE → JS Date | 带上本地时区，而 Oracle DATE 无时区 | 会话固定 NLS 格式后按字符串取回 |
| `oracledb.DATE` 别名 | **实际指向 TIMESTAMP**，漏掉真正的 DATE 与带时区类型 | 逐个列全 7 个类型常量 |

**连接串**：服务名走 EZConnect（`host:port/service`），SID 必须展开成完整 `DESCRIPTION`
（EZConnect 不支持 SID），猜错直接 ORA-12514/12505，因此连接对话框提供显式单选。

**未做**：包（Package）、同义词、物化视图——OB-Oracle 也没有，属对象覆盖面扩展，可后续单独加。

## 第 5 批：非关系型（Redis → Elasticsearch/OpenSearch → MongoDB）

这批与本产品的表格化 UI **结构性不契合**，每个都要新的界面形态，容易做成半成品。
一律按下方 ES 的评估口径处理：**严格限定为只读浏览 + 查询，不做管理功能**。
顺序理由：Redis 数据模型最简单、界面改动最小；ES 次之；MongoDB 最重，放最后。

### Elasticsearch / OpenSearch 的定位（2026-08-18 评估）

**结论：可以做，但必须严格限定为「查数据」，不做「管 ES」。**
Kibana 常被运维锁住、开发拿不到，工具空白是真实的；Navicat 完全不支持 ES，属差异化项。

**做什么**：

- 索引与别名浏览（`_cat/indices`、`_alias`）、mapping 查看（等价于"查看定义"，只读）。
- 查询编辑器走 ES SQL API（`POST /_sql`，Basic 免费层即有；OpenSearch 走 `_plugins/_sql`）。
- 表数据浏览走 `_search` 的 `from`/`size`，导出复用现有五格式管线。
- 认证支持 Basic / API Key，HTTPS 支持"信任服务器证书"（同 SQL Server），可经 SSH 隧道。
- **零新依赖**：Node 18+ 的全局 `fetch` 足够，不引 `@elastic/elasticsearch`（该客户端与服务端大版本强耦合，
  会变成长期维护负担）。

**不做**（写死在设计里，避免半成品）：

- 索引管理、mapping 编辑、分片/副本调整、集群运维——那是 Kibana 的活。
- 文档编辑：ES 文档有 `_id`，单文档改删技术上可行，但 ES **无事务**，
  与本工具"编辑在事务中提交、失败整体回滚"的承诺冲突。**网格只读**，与 ClickHouse 同策略。
- 聚合、嵌套文档、相关性评分的可视化——网格渲染不了。
- 表设计器、数据同步、结构同步、备份：一律不开放。

**已知的架构落差**（实现前必须先解决）：

| 落差 | 说明 | 处置 |
|---|---|---|
| 无 database/schema 层级 | 树是"连接 → 数据库 → 表" | 退化为单个伪库，索引即表。**已有先例**：[sqlite.js:180](../src/main/db/sqlite.js) 的 `listDatabases()` 直接返回 `['main']` |
| ES SQL 不支持 `OFFSET` | `base.pageSql(select, order, limit, offset)` 的翻页模型对不上 | 表浏览改走 `_search` 的 `from`/`size`；受 `index.max_result_window`（默认 10000）限制，超出时**明确拒绝并提示加筛选**，不静默截断 |
| 无事务 | `transactionSupport` 返回 false | 同 ClickHouse，查询标签仅自动提交 |
| mapping 不可变 | 已有字段类型改不了，只能加字段 | 不提供表设计器，只提供 mapping 只读查看 |

**参考实现**：[clickhouse.js](../src/main/db/clickhouse.js) 是最接近的先例——HTTP 接口、网格只读
（`readonlyReason`）、能力按 `objectCaps` 裁剪、`transactionSupport` 关闭。

**待确认**：是否一并支持 OpenSearch（endpoint 与部分语法不同，增量成本约 20%，但国内云厂商的
"ES 服务"多数其实是 OpenSearch 分支，不支持会有相当比例的用户连不上）。
